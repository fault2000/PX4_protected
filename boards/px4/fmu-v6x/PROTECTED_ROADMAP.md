# FMUv6X protected 이식 후속 계획

갱신 기준: 2026-09-15, `v0.1.4` 대기 중인 uORB 구독자 진단 구현·빌드·정적 검사 완료, 실기 대기.
실기 확인 기준: 초기 부팅 PX4 `03ca855b52`, 초기 HRT `eafec6aa20`, 워크큐·HRT 회귀 `963c07808e`.
uORB 및 공통 서비스 회귀 기준: PX4 `a69eb3fa3f`, GCC 13.2.1, 빌드 시각 `Sep 15 2026 17:43:18`.
공통 기반: NuttX `5ef31ffdf1`, NuttX apps `e37940d853`.
현재 확인된 결과와 앞으로 수행할 작업을 구분한다. 단계별 통과 조건은 검증 계획이다.

## 연구 버전 규칙

연구 버전은 이 개인 저장소의 작업 진도를 나타내며, 기반 PX4 버전 `1.17.0`과
별도로 관리한다. 2026-09-15 사용자 요청에 따라 **작업 묶음 완료 시에만 Git annotated
tag를 만들고, 패치 번호는 커밋 제목과 아래 변경 기록에 표기**한다. Git push 자체에는
별도 버전 메시지란이 없으므로 `[v0.1.2] work_queue: ...`와 같은 커밋 제목으로 게시한다.
이미 게시한 `v0.1`과 `v0.1.1` 태그는 과거 기준점으로 유지한다. 같은 날 사용자가 요청한
USB 재접속 문서 정정으로 두 태그를 한 번 갱신했으며, 이후에는 고정한다.

| 버전 표기 | 의미와 기록 방식 |
| --- | --- |
| `v0.1` | 최소 protected 부팅, USB NSH 접속·재접속, 기본 힙·태스크 진단과 초기 uORB 메시지 읽기를 확인한 기준 |
| `v0.1.1` | 기존 HRT 패치 태그 보존. 구현·빌드 및 기본 실기 2회 통과를 아래 기록으로 확정 |
| `v0.1.2`, `v0.1.3`, … | 다음 작업 묶음 안의 수정·기능 추가. 커밋 제목·변경 기록에만 표기하고 태그는 만들지 않음 |
| `v0.2` | HRT·사용자 워크큐·uORB 공통 실행 경로의 정비와 합의된 실기 검증 완료 후 태그 생성 |
| `v0.2.1`, … → `v0.3` | 패치는 커밋으로 추적하고, 다음 작업 묶음 완료 시 `v0.3` 태그 생성 |

작업 묶음을 시작할 때 범위와 통과 조건을 이 문서에 정한다. 개별 수정이나 빌드 성공만으로
minor 버전을 올리지 않고, 해당 묶음의 구현과 실기 검증을 마친 뒤 올린다. 문서만 수정한
커밋마다 패치 번호를 올리지 않는다. 태그와 변경 사항은 `fault2000/PX4_protected`에
게시하며, NuttX 변경이 필요하면 `fault2000/nuttX`에서 관리한다.

`v0.1`의 실기 근거는 위의 `03ca855b52` 펌웨어다. 이 기준에 검증 기록·로드맵과
연구 태그를 지원하는 빌드 버전 선택 변경을 더한다. 빌드의 PX4 버전 계산은 `v0.*`를
제외하여 `1.17.0`을 유지한다. 상위 저장소의 태그에는 NuttX/apps gitlink도 고정되므로
같은 이름의 서브모듈 태그는 필요 없다. 생성된 `.px4`·ELF·map은 Git 태그에 자동으로
포함되지 않으며, 실기 결과에는 사용한 도구 버전과 정확한 산출물을 대응시킨다.

## 목표와 현재 위치

목표는 PX4 v1.17의 필요한 비행 기능을 NuttX protected 환경에서 실행하고,
의도한 커널·유저 배치와 실시간 동작을 실제 FMUv6X에서 확인하는 것이다.
우선 멀티콥터의 센서 → 추정 → 제어 → 출력 경로를 완성하고, 이후 default 구성의
기능별 지원 여부를 관리한다. 기체 유형이 달라지면 제어기 복원 단계부터 조정한다.

NuttX protected의 보호 범위는 커널과 사용자 영역 사이이다. 사용자 모듈들은
하나의 사용자 영역을 공유한다. 모듈마다 독립된 주소 공간이나 장애 복구를 제공하는
설계는 별도 과제다. [NuttX의 빌드 구성 설명](https://nuttx.apache.org/docs/latest/guides/usingkernelthreads.html)을 참고한다.

| 항목 | 현재 확인된 상태 |
| --- | --- |
| 최소 protected 타깃, 커널·유저 ELF, 통합 `.px4` 생성 | 빌드 및 정적 산출물 검사 완료 |
| 메모리 배치, STM32H7 protected heap/MPU 및 할당 함수 링크 보정 | 정적 검사 완료, 기존 두 부팅 HardFault 지점 통과 확인 |
| Native USB NSH | Windows COM3 열거와 Enter 세 번 후 `nsh>` 진입 확인. USB 재접속 후 NSH 사용 성공도 사용자 확인으로 검증 완료 |
| 초기 부팅 | GCC 13.2.1 실기 이미지에서 초기화 스크립트와 버전·사용자 워크큐 상태 출력 확인 |
| 초기 진단 명령 | `help`, `free`, `ps`, `uorb status`, `listener log_message -n 1` 실행 확인 |
| 힙·태스크 상태 | `a69eb3fa3f`의 uORB 예열 후 반복과 HRT·워크큐 회귀 뒤 Kmem 여유 207,632 B·Umem 여유 107,792 B 유지. uORB 직후 `usr_uorb` 스택 420/1,488 B, `usr_hrt` 420/960 B, 사용자 큐 관리자 620/1,232 B. 종료 워커의 스택 사용량은 미수집 |
| uORB 기본 데이터 경로 | 커널의 초기 `log_message`를 사용자 listener로 구독·복사·해제하는 경로 확인 |
| HRT 전달·취소 패치와 사용자 진단 명령 | `v0.1.1`에서 구현. 호스트 8개·빌드·정적 검사에 더해, GCC 13.2.1 실기 이미지에서 `hrt_smoke run` 연속 2회 통과 |
| HRT 콜백 실행 영역 | 콜백 PID 7이 `ps`의 `usr_hrt`와 일치. `CONTROL=0x7`의 nPRIV=1로 비특권 실행 확인 |
| 사용자 워크큐 패치와 진단 명령 | `963c07808e`에서 실기 4회 통과. 워커 PID 13·15·28·30의 비특권 실행, 취소·중지·재시작과 제어 Run 6회 후 워커 종료 확인. 종료 후 사용자 큐 0개, 같은 이미지 HRT 회귀도 통과 |
| uORB 사용자 콜백 정비와 진단 명령 | `a69eb3fa3f`에서 기본 실기 3회 통과. 사용자 콜백 PID 9 CONTROL=0x7, 커널 콜백 PID 15·28·31 CONTROL=0x4. K→U/U→K/U→U/K→K 전달, pending 해제·재등록·병합·self-unregister·WorkItem 실행과 임시 워커 종료 확인 |
| uORB 대기·timeout·제한된 주기 발행 진단 | `v0.1.4`에서 4개 조합의 `uorb_wait_smoke run` 구현. 실제 API 대기 세마포어와 TCB waitsem을 비교하여 발행 전 대기를 확인하도록 구성. 실기 검증 대기 |
| MPU 접근 차단, 다중 워커·장시간 운용, HRT 다중 타이머·적체, uORB blocking wait·주기 부하 | 후속 실기 검증 필요 |
| PX4 센서·출력 드라이버와 비행 모듈 | 현재 최소 타깃에서 비활성화 |

상세 구성과 기존 검사 방법은 [PROTECTED.md](PROTECTED.md)에 있다.
실기 로그의 PX4/NuttX 해시가 위 기준과 일치한다. `Work Queue: 0 threads`는
사용자 워크큐 관리자가 실행 중이고 현재 작업용 큐가 없다는 뜻이다. 초기 부팅 때는
미생성 상태였고, 워크큐 실기 후에는 검사 큐의 종료·정리를 확인한 상태다. 커널 워크큐까지
0개라는 의미는 아니다. 초기 명령과 USB 재접속 결과는 확인했다. 재접속 반복 횟수는
보고에 기록되지 않았으므로 기존 10회 계획의 횟수 충족까지 추정하지 않는다.
HRT 기본 일회성·주기 콜백, 만료 전 취소, NULL 콜백 만료, 취소 후 정지와 재사용은
두 번의 실기 실행으로 확인했다. 매번 전달 8회, 종료 시 pending=0, coalesced 증가=0이었고
검사 전후 힙 통계도 동일했다. 이후 `v0.1.2`에서 워크큐 기본 검사를 총 4회 통과했고,
동일 이미지의 HRT 회귀도 통과했다. 힙 변화는 추가 실행에서 누적되지 않았으며 NuttX의
지연 스택 반환·시그널 풀 재사용 설명과 부합한다. 할당 주소를 추적해 소유자를 확정한 것은
아니다. 상세 수치와 관찰 한계는 [PROTECTED.md](PROTECTED.md)에 기록했다.
uORB 알림·콜백 경계 정비는 `v0.1.3`에서 구현하고 `a69eb3fa3f` 실기에서 기본 검사 3회와
HRT·워크큐 회귀를 통과했다. 매번 알림 전달 7회·병합 7회, 종료 시 registered/pending=0이었다.
첫 실행 이후 사용 메모리는 누적 증가하지 않았다. 최종 Umem nfree만 3→4로 변했으며
used/free/largest는 유지됐다. 할당 소유권이나 장시간 누수 여부까지 확정한 결과는 아니다.
`v0.1.3`의 poll 검사는 발행 후 준비 상태와 읽기 후 해제만 확인한다. `v0.1.4`는 실제 대기
중인 `poll()`과 `SubscriptionBlocking`의 깨우기·timeout·제한된 주기 발행 진단을 추가했다.
다음은 새 이미지의 `uorb_wait_smoke run` 반복 실기와 기존 uORB·HRT·워크큐 회귀다.
반복 부팅·유휴 관측과 이후 부하·지연 검증은 별도로 이어간다.
`listener -n 1`의 저장된 메시지 읽기만으로 이들을
통과 처리하지 않는다. `free`의 `Prog` 행에는 마지막 32바이트 페이지를 추가로
집계하는 표시 문제가 있으므로 RAM 평가는 Kmem/Umem 행을 기준으로 한다.

## 단계별 작업과 통과 조건

단계는 의존성 순서다. 메모리와 실행 시간 측정은 모든 단계에서 반복한다.
아래 반복 횟수와 관측 시간은 초기 개발용 제안이며 비행 적합성 판정 기준은 아니다.

| 단계 | 작업 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 0. 기준 고정 | 현재 커밋으로 clean build, 서브모듈·도구 버전·설정·ELF/map·체크섬 보관. 실제 보드 리비전, 센서, 복구 수단 확인 | 기존 정적 검사 통과. 보드에 올릴 파일과 소스 커밋의 대응 확인. flat 비교용 기준 확보 |
| 1. 실기 부팅과 콘솔 | USART3 초기 로그와 USB NSH 접속·명령·재접속 확인. 커널·유저 초기화 결과 및 실패 표시와 반복 운용 기록 보강 | USB 재접속 성공은 사용자 확인 완료(기존 10회 계획의 실제 횟수는 미기록). 냉간 부팅 10회·유휴 30분 동안 설명되지 않은 fault·정지 없는지는 별도 검증 필요 |
| 2. 실행 영역과 공통 서비스 | 모듈별 영역 표 작성, HRT·uORB·워크큐 경계 정비, 힙 소유권·파라미터·events·파일 I/O 검증 | ELF 배치와 런타임 실행 권한 일치. 타이머 전달·취소, 양방향 pub/sub·poll·콜백, 저장 후 재부팅 복원 검증 |
| 3. 통신과 로그 | 별도 TELEM UART에 MAVLink 복원, logger와 필요한 dataman 경로 복원 | QGC 연결·파라미터 조회/변경, SD 기록·읽기 확인. USB NSH 접근 유지 |
| 4. 센서 | 실제 보드의 IMU 1개부터 시작하여 baro/mag/전원/GPS 등 필요한 센서와 sensors 모듈 복원 | 커널 드라이버 → uORB → 유저 소비자 경로 확인. ID·축·단위·주기·timestamp·오류 카운터를 flat과 비교 |
| 5. 상태 추정과 제어 | EKF2 단일 인스턴스부터 commander/events, RC/manual_control, land_detector, 비행 모드 관리, MC 제어기와 control_allocator 순으로 통합 | 물리 출력 없이 추정 상태·제어 토픽·arming 조건·모드 전이·입력 단절 처리 확인. 각 모듈의 목표 실행 영역 확인 |
| 6. 실제 출력 | 사용할 PWM 또는 DShot/PX4IO 경로와 관련 safety 기능 복원 | 프로펠러를 제거한 벤치에서 출력 계측. 채널·주기·disarm·failsafe·재부팅 시 동작 확인 |
| 7. 기능 확대와 회귀 | 중복 센서/EKF, navigator, 필요한 CAN/DDS/네트워크 및 기타 기체 기능을 단계적으로 복원 | default 대비 기능 지원 표와 성능 비교 보고서 작성. 장시간·반복·복구 시험과 HIL 등 가능한 지상 시험 통과 후 비행 검증 조건 결정 |

MAVLink나 logger의 추가 의존성이 드러나면 해당 의존 모듈만 먼저 포함한다.
전체 `rcS` 또는 `rc.board_sensors` 복원은 개별 경로가 검증된 다음으로 미룬다.

## 커널·유저 배치 초안

최소 구성은 진단 기준으로 유지하고, 비행 기능 확대 구성은 별도 타깃으로 관리한다.
다음 배치는 목표안이며 라이브러리 의존성 및 실행 시간 측정으로 확정한다.

| 대상 | 목표 영역 | 경계를 넘는 방법/검토 사항 |
| --- | --- | --- |
| NuttX, MPU, IRQ, 하드웨어 타이머, GPIO/SPI/I2C/DMA 및 출력 드라이버 | 커널 | 장치 API 또는 명시적인 syscall/boardctl 인터페이스 |
| uORB 저장소 및 커널 측 파라미터·events 서비스 | 커널 | 유저 proxy를 통한 요청·데이터 전달. 객체와 버퍼 소유권 명시 |
| 사용자 콜백, 사용자 워크큐 | 유저 | 커널은 알림을 전달하고 유저 dispatcher가 콜백 실행. 취소·등록 해제·종료 계약 필요 |
| sensors의 처리 로직, EKF2, commander, 비행 모드 관리, 제어기, control_allocator | 유저를 목표 | 직접 하드웨어 접근 및 커널 전용 라이브러리 의존성 제거·분리 |
| NSH, MAVLink, logger, dataman 등 응용 기능 | 유저를 목표 | 장치/파일/서비스 API 사용, 표준 입출력과 종료 상태 전달 확인 |

현재 [cmake/kconfig.cmake](../../../cmake/kconfig.cmake)는 활성 모듈 중 userspace 목록에
없는 모듈을 커널로 분류한다. EKF2, sensors, MC attitude/rate controller의 `USER_*`
기본값은 `n`이고, commander, MAVLink, logger, control_allocator는 `y`다.
따라서 모듈 활성화와 사용자 영역 이식 완료를 별도로 관리한다. 각 모듈에 대해
설정값, 최종 ELF/라이브러리 배치, task 종류, 콜백 실행 영역을 기록한다.

## 모듈 확대 전에 해결할 경계 문제

다음은 현재 소스에서 확인한 구조다. 실기에서 오류가 재현되었다는 의미는 아니다.

1. **초기화 성공과 진단 범위**
   - [px4_userspace_init.cpp](../../../platforms/nuttx/src/px4/common/px4_userspace_init.cpp)는
     기반 서비스의 초기화 결과를 상위에 전달하지 않는다. 단계별 성공·실패 기록과
     HRT dispatcher, 커널·유저 워크큐의 생존 확인을 추가한다.
   - 현재 `work_queue status`는 유저 명령이다. 이 출력만으로 커널 워크큐까지
     정상이라고 판단하지 않고 양쪽 상태를 별도로 관측한다.
2. **HRT 이벤트 전달·취소**
   - `v0.1.1`의 [hrt_ioctl.c](../../../platforms/nuttx/src/px4/common/hrt_ioctl.c)는
     FIFO와 타이머별 대기 1개 정책을 사용한다. 이미 대기 중인 주기 만료는 병합하고
     횟수를 기록한다. 별도 고정 용량 제한이나 IRQ 내 메모리 할당은 없다.
   - 취소·재예약은 kernel timer와 pending 알림을 같은 IRQ 임계 구역에서 정리한다.
     단일 코어 [usr_hrt.cpp](../../../platforms/nuttx/src/px4/common/usr_hrt.cpp)는
     scheduler lock으로 dequeue부터 짧은 비차단 콜백의 완료까지 수명을 보호한다.
     오류 반환·NULL 콜백을 처리하고, 오류 로그는 바깥 lock 해제 후 출력한다.
   - 실제 두 소스를 사용하는 호스트 동작 검사 8개에 이어, `eafec6aa20`의 GCC 13.2.1
     이미지에서 `hrt_smoke run`이 연속 2회 통과했다. 일회성·주기·만료 전 취소·NULL 콜백·
     취소 후 정지·재사용과 비특권 콜백 실행을 확인했다. 주기 관찰값은 99,999--100,000 us였다.
   - 100 ms 단발성 예약의 8--15 us 초과 관찰값은 API·syscall·전달 비용을 포함한다.
     NULL 콜백의 약 109 ms는 10 ms 간격 polling으로 만료를 발견한 시점이다.
     두 실행의 짧은 측정으로 최악 지연이나 장시간 안정성을 판정하지 않는다.
   - 다중 타이머 FIFO·대기 교체·적체와 콜백 내부 취소·재예약은 별도 실기 검증이 남는다.
     기존 사용자 `hrt_call_delay()` wrapper 부재 등 전체 API 동등성도 후속 항목이다.
3. **uORB 콜백 실행 영역**
   - `v0.1.3`의 [uORBManagerUsr.cpp](../../../platforms/common/uORB/uORBManagerUsr.cpp)는
     사용자 콜백 객체를 사용자 map에 보관한다. 커널의
     [uORBUserCallback.cpp](../../../platforms/common/uORB/uORBUserCallback.cpp)는 객체 포인터
     대신 재사용하지 않는 정수 토큰과 node handle만 보관한다. 기존 커널 콜백은 별도로 유지한다.
   - 등록은 최대 64개이며 publish 시 고정 배열을 순회한다. 알림은 등록별 1개까지 FIFO에
     대기하고 중복은 병합한다. IRQ 경로에서 동적 할당하지 않는다. 데이터 보존 범위는
     기존 토픽 큐의 깊이에 따르며, 알림 횟수와 발행 횟수가 같다고 가정하지 않는다.
   - `usr_uorb`는 우선순위 254, 요청 스택 1,536 B의 상시 사용자 태스크다. 단일 코어의
     scheduler lock으로 토큰 수신부터 짧은 비차단 콜백까지 보호한다. 콜백은 할당·출력·대기를
     하지 않아야 한다. 등록 해제는 사용자 map을 먼저 지우고 커널 등록과 pending을 제거한다.
     콜백 내부 해제는 허용하되, 파생 자원이나 연결된 WorkItem을 파괴하기 전에 해제하고 작업도
     정지시켜야 한다. signal handler의 호출과 여러 소유자의 동시 수명 변경은 지원하지 않는다.
   - `SubscriptionBlocking`은 등록 실패 시 대기하지 않고, protected user에서 상태 재확인과
     조건변수 대기 사이의 선점도 막는다. 해당 blocking 경로 실기 검증은 별도로 남는다.
     `SubscriptionCallback::unsubscribe()`는 비가상이므로 base reference로 호출하는 경우까지
     보호하지 않는다. dispatcher가 시작된 뒤 Manager 종료는 `EBUSY`로 거절한다.
   - `uorb_smoke run`은 U→U의 poll 준비 상태·복사·콜백, pending 해제·재등록·8회 발행 병합·
     self-unregister와 실제 `SubscriptionCallbackWorkItem`을 검사한다. 기존 고정 builtin을
     통해 실행한 별도 커널 태스크가 U→K 수신, K→K 콜백, K→U 응답을 검사한다.
     실제 커널 알림 소스의 호스트 7개, 펌웨어 빌드·정적 배치 검사에 이어 `a69eb3fa3f`에서
     실기 3회도 통과했다. 사용자 콜백과 커널 콜백의 nPRIV 값, registered/pending=0,
     두 종류 검사 워커의 종료 및 `usr_uorb` 스택 420/1,488 B를 확인했다.
   - 첫 실행은 두 진단 토픽의 node·버퍼를 남기므로 예열 후 반복 힙을 비교한다. 부하 중 주기
     발행, blocking poll 깨우기, 다수 구독자, 지연·장시간 검증은 별도 항목이다. 이번 변경으로
     기존 ioctl의 모든 포인터 검증이나 MPU 접근 차단을 확인한 것으로 취급하지 않는다.
   - `v0.1.4`의 `uorb_wait_smoke`는 실제 pollfd.sem 또는 SubscriptionBlocking의 조건변수
     세마포어와 호출자 TCB의 waitsem을 비교한다. 보조 진단은 사용자 BSS의 식별자 저장공간을
     확인하고 호출한 태스크만 관찰한다. 객체 배치나 공개 API 변경 없이 진단용 friend 선언으로
     조건변수의 식별자를 얻는다. 관찰·생산 태스크는 종료를 확인한 뒤 저장공간을 재사용한다.
   - 각 조합은 200 ms 무발행 timeout 2회와 발행 6회를 검사한다. 발행 5회는 100 ms 절대
     기한을 유지하고, 마지막 1회는 timeout 뒤 재사용을 확인한다. 깨우기 대기는 최대 1초이며
     정상 수신은 500 ms 이내여야 한다. 발행 지각 한도 50 ms는 기능 확인용 범위이며 최악 지연
     보장이 아니다. 실제 지연·주기·시퀀스 결과와 힙·스택·종료 상태는 보드에서 수집한다.
4. **메모리 및 장치 접근**
   - 현재 user heap은 128 KiB이고, 일반 할당 영역은 AXI SRAM으로 제한되어 있다.
     기능 추가마다 정적 RAM·힙 최대 사용량·스택 여유·flash 크기를 측정한다.
   - 양쪽 allocator의 할당/해제 소유권, 공유 버퍼 수명, DMA 버퍼 위치와 cache
     처리 요구를 확인한 후 다른 SRAM 사용이나 flash/RAM 분할 변경을 결정한다.
   - MPU 설정, 스레드 권한, 허용 접근 범위와 fault 처리 정책을 보드에서 점검한다.
     사용자 task 오류가 해당 task만 종료한다고 가정하지 않는다.

## 검증과 변경 관리

- 단계별 변경을 작게 나누고, 설정·시작 스크립트·ELF 배치 증거·UART/USB 로그를 함께 남긴다.
- HRT/uORB/워크큐에는 해당 계약을 검증하는 집중 시험을 추가한다. 현재 최소 타깃에는
  광범위한 PX4 `tests` 명령이 없으므로 사용할 시험 모듈과 실행 방법도 명시한다.
- 커널·유저 힙과 스택, CPU, 센서→제어→출력 지연, 최악 지연과 주기 편차, topic 손실,
  SD 기록 중 부하를 측정한다. 동일 보드·센서 설정의 flat 결과와 비교하고 기능별 허용
  지연과 자원 여유 목표를 정한다. 전체 평균만으로 제어 주기 충족을 판단하지 않는다.
- flat/protected clean build는 별도 소스 디렉터리와 독립된 NuttX 서브모듈에서 수행한다.
  두 PX4 build 디렉터리가 같은 NuttX 생성 상태를 공유한 채 병렬 빌드하지 않는다.
- 보드별 센서 선택은 [rc.board_sensors](init/rc.board_sensors)의 리비전 분기를 참고한다.
- 초기 USB `/dev/ttyACM0`의 소유자는 native NSH로 유지한다. USB MAVLink까지 필요해지면
  별도 인터페이스 또는 명시적인 전환 방식을 설계한다.
- default의 각 기능을 미착수/빌드 확인/실기 확인/지원 제외로 관리한다. 초기 최소 비행
  경로 완료와 default 전체 기능 대응 완료를 별도로 기록한다.

## 바로 다음 작업 묶음: v0.2

범위는 HRT → 사용자 워크큐 → uORB 알림으로 이어지는 공통 실행 경로다.
단계 2 전체나 센서·비행 기능 복원 완료를 뜻하지 않는다. 아직 확인하지 않은 파라미터,
events, 파일 I/O 및 MPU 접근 차단 검증 등은 각각의 후속 작업으로 계속 추적한다.

1. HRT 이벤트 전달·취소 계약을 정리하고 사용자 영역의 작은 NSH 진단 명령을 추가한다.
   one-shot은 정확히 한 번 실행되고, periodic은 주기·횟수를 기록하며, 취소·정리 완료
   후 추가 실행이 없어야 한다. 콜백의 ELF 배치와 실제 실행 영역을 확인한다.
   `v0.1.1`에서 구현·호스트 검사·빌드·정적 배치와 기본 실기 2회 통과를 확인했다.
   `free` 전후 통계와 `ps`의 실행 태스크·스택도 확보했다. 기본 검사 단계는 통과이며,
   다중 타이머·적체·장시간 동작은 별도 검증으로 추적한다.
2. 사용자 워크큐에서 실제 작업을 실행하여 주기, 중지, 재시작을 검증한다.
   반복 실행 후에도 콘솔 응답과 힙·스택 사용량이 안정적인지 기록한다.
   `v0.1.2`에서 구현·빌드·정적 검사와 기본 실기 4회 통과를 확인했다. 실제 비특권
   `ScheduledWorkItem::Run()` 실행, 중지·재시작과 워커 종료 후 객체 정리를 확인했다.
   같은 이미지 HRT 회귀도 통과했다. 반복 후 힙은 같은 수준을 유지했으며, 지연 반환과
   재사용 풀의 영향을 기록했다. 다중 워커·장시간·종료 워커 스택 계측은 후속 검증 항목이다.
3. uORB의 K→U, U→K, U→U 및 K→K 경로에서 주기 발행·구독·poll 알림과 콜백을
   검증한다. 유저 콜백은 유저 영역에서 실행되고, 구독 해제·종료 후 수명이 끝난 객체에
   알림이 전달되지 않아야 한다. 누락과 지연을 측정한다.
   `v0.1.3`에서 경계 정비·진단·빌드·호스트 검사와 기본 실기까지 완료했다. `a69eb3fa3f`로
   예열 1회와 반복 2회, 등록/pending 원상 복귀, 검사 워커 종료, 힙·상시 태스크 스택 기록과
   HRT·워크큐 회귀를 확인했다. `v0.1.4`에서 실제 대기의 깨우기·유한 timeout·재대기와
   sequence/timestamp 기반 제한된 주기 발행 진단을 구현했다. 다음 실기는 새 진단의
   예열 1회와 반복 2회, 네 조합별 관찰 8회·수신 6개, 구독 등록/pending 복귀, 임시 태스크
   종료, 힙·상시 태스크 스택 기록 및 기존 진단 회귀다. 이 진단의 구현만으로 실기나 부하·
   장시간 검증을 통과 처리하지 않는다.
4. 단계 1의 반복 부팅·유휴 관측을 병행한다. USB 재접속 동작은 확인 완료했으며,
   후속 펌웨어의 회귀 점검 항목으로 유지한다. 각 패치의 빌드 결과와 실기
   결과를 구분해 기록하고, 이 묶음의 모든 통과 조건이 충족되면 `v0.2` 태그를 만든다.

이후 통신·로그와 센서 복원 작업의 범위를 정하고, IMU 1개에서 사용자 소비자까지
연결한다. 남은 주요 불확실성은 blocking 구독과 주기 부하, 반복 운용 안정성, 기능 확대 시의
메모리·실시간 여유다. 일정은 위 검증 결과를 보고 산정한다.
